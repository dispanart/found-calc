# Found Calc Phase 04 — Persistence, Auth & Guest Preservation Design

**Status:** implementation baseline for the already-approved Phase 04 slot in Found Calc Phase Workflow v2  
**Date:** 2026-08-28  
**Predecessor:** Phase 03 — Product UI Runtime & Discovery  
**Successor:** resolved by the canonical Phase Workflow at handoff; Phase 05+ scope is not pulled forward here.

## 1. Purpose

Phase 04 adds the first durable product-state boundary without moving calculation truth out of the Phase 02/03 local deterministic runtime. A visitor must remain able to calculate without an account, preserve a calculator draft locally, explicitly persist the latest canonical draft to first-party D1, create/sign in to an account, and claim previously persisted guest drafts without losing calculator identity or locale behavior.

The phase proves persistence and authentication as infrastructure/product boundaries. It is not the phase for project/history features, billing, production rule data, remote provisioning, analytics, AI explanations, or admin publishing.

## 2. Fixed boundaries inherited from Phase 01–03

- `@found-calc/engine` remains the only formula-truth owner and receives no auth, D1, React, locale, or network dependencies.
- `@found-calc/rules` remains the immutable effective-date/version resolver and receives no persistence/auth responsibilities.
- `@found-calc/catalog` remains discovery/product metadata only.
- Reference calculation execution remains local in `apps/web`; no server calculation API is introduced.
- Canonical decimal strings are the persistence boundary for numeric calculator inputs. D1 never becomes a place to recompute or normalize formulas.
- ID/EN, keyboard operation, field-error association, polite status regions, synthetic fixture warnings/provenance, and 390px no-overflow remain regression requirements.
- Fixed infrastructure stays within the Rp0 target using local/free-tier-compatible Cloudflare primitives; no remote D1, DNS, credential, or paid-service mutation is performed in Phase 04.

## 3. Phase 04 scope

### 3.1 D1 schema and repository

Use the existing `DB` D1 binding. Add one checked-in migration containing:

1. Better Auth core SQLite tables required for email/password sessions: `user`, `session`, `account`, and `verification`.
2. `calculator_state`, a deliberately narrow product table storing at most one latest persisted draft per `(owner_type, owner_id, calculator_id)`.

`calculator_state` fields:

- `id`: text primary key generated by the application;
- `owner_type`: `guest | user` checked at the database boundary;
- `owner_id`: opaque guest token or Better Auth user ID;
- `calculator_id`: stable Phase 03 catalog ID;
- `calculator_version`: engine calculator version used when the draft was validated;
- `state_json`: validated JSON containing canonical calculator inputs only;
- `updated_at`: integer epoch milliseconds.

The table stores no localized number strings, rendered HTML, passwords, auth tokens, result arithmetic, telemetry, billing data, or production regulatory data.

Drizzle ORM provides the typed product repository over D1. The repository exposes read/upsert/delete and deterministic guest-to-user claim operations. Claim is idempotent: for each calculator, the newer `updated_at` state wins; after successful user ownership is established, the guest row is removed.

### 3.2 Guest identity

Unauthenticated persisted state is owned by a cryptographically random opaque UUID in a first-party `found_calc_guest` cookie.

Cookie contract:

- `HttpOnly`;
- `SameSite=Lax`;
- `Path=/`;
- `Secure` outside local development;
- no device fingerprinting and no third-party identifier;
- created only when a guest performs a persistence mutation, not merely by visiting a calculator.

The cookie is an ownership capability, not user profile data. It must never be exposed to client JavaScript.

### 3.3 Better Auth

Use Better Auth stable `1.6.x` with its Next.js App Router handler and the existing D1 binding. Phase 04 enables email/password sign-up, sign-in, sign-out, and session retrieval only.

Explicit exclusions: email verification delivery, password reset delivery, OAuth/social providers, organizations, roles/admin authorization, 2FA/passkeys, billing plugins, and production secret provisioning.

Runtime configuration reads `BETTER_AUTH_SECRET` and optional `BETTER_AUTH_URL` from Worker bindings/environment. A committed `.dev.vars.example` documents local keys but contains no secret value. The canonical Next.js build remains supported by aliasing `cloudflare:workers` to a non-executing build stub only for Turbopack; vinext/Workers uses the real module.

### 3.4 Product persistence API

Add first-party route handlers:

- `GET /api/calculator-state/:calculatorId` — returns the current owner’s latest persisted canonical state or 404;
- `PUT /api/calculator-state/:calculatorId` — validates catalog ID, calculator version, JSON size/shape, and canonical decimals before upsert; authenticated session ownership wins, otherwise a guest cookie is created and used;
- `DELETE /api/calculator-state/:calculatorId` — deletes the current owner’s saved state;
- `POST /api/guest/claim` — requires an authenticated Better Auth session, claims rows owned by the current guest token, clears the guest cookie only after success, and is safe to repeat.

The server accepts only the three Phase 03 reference calculator state shapes. Validation code may verify decimal/date syntax and catalog identity, but must not calculate totals, margins, scenarios, rates, or recommendations.

### 3.5 Browser draft preservation

A small client-side draft helper uses `localStorage` to preserve in-progress UI state across locale navigation and reloads for the three reference calculators. This local draft can contain localized form strings because it never crosses the engine or D1 boundary.

Requirements:

- namespaced key includes stable calculator ID and a schema version;
- browser storage access occurs only in client effects/event handling;
- malformed/unknown stored data is ignored and removable;
- no auth/session token is stored in `localStorage`;
- no automatic network persistence occurs on keystroke.

This closes the Phase 03 limitation where locale switching loses unsaved form state without silently transmitting raw input.

### 3.6 Calculator integration

Each reference calculator:

- restores its local in-progress draft on mount;
- updates the local draft as form state changes;
- after a successful local deterministic calculation, can explicitly **Save draft** to D1 using canonical inputs already accepted by the engine/runtime;
- can load a persisted draft and map canonical values back to locale display strings;
- can remove the persisted draft;
- communicates save/load/remove status through an accessible polite status region;
- clearly states that calculation still happens locally and only the saved draft is sent to Found Calc storage.

No full calculation history, naming/tagging, projects, collaboration, or server-side result replay is added.

### 3.7 Account UI and guest claim

Add localized `/{locale}/auth` with accessible email/password sign-up and sign-in forms. After successful sign-up/sign-in, the client calls `POST /api/guest/claim` once, then refreshes session UI. Failure to claim must not invalidate the successful sign-in; it surfaces a clear retryable preservation warning.

The header exposes account state without blocking public calculators. The existing workspace shell becomes an authenticated persistence summary surface: signed-out users see a sign-in prompt; signed-in users see identity plus which of the three calculator drafts currently exist. This is not a Goals/Projects workspace.

## 4. Data validation contracts

Persisted canonical state types:

```ts
type PersistedCalculatorState =
  | {
      calculatorId: "reference.discount";
      calculatorVersion: string;
      input: { baseAmount: string; discountPercentages: string[] };
    }
  | {
      calculatorId: "reference.business-margin";
      calculatorVersion: string;
      input: {
        sellingPrice: string;
        productCost: string;
        variableSellingCostPerOrder?: string;
        scenarioVariableSellingCostPerOrder?: string;
      };
    }
  | {
      calculatorId: "reference.synthetic-rule";
      calculatorVersion: string;
      input: { baseAmount: string; effectiveDate: string };
    };
```

Validation reuses catalog IDs and engine input/version contracts where practical. It must reject exponent syntax, localized separators, unknown properties, excessive array lengths, invalid ISO dates, unsupported calculator IDs/versions, and payloads over 16 KiB.

## 5. Error handling

- Auth errors are localized at the form boundary and never reveal whether an unrelated account exists beyond Better Auth’s safe response.
- D1/API errors return stable machine codes and generic user copy; internal SQL details are not exposed.
- A failed save never replaces the last known successful local calculation result.
- A failed persisted-draft load never overwrites the in-progress local draft.
- Guest claim runs transactionally/batched where D1 semantics allow; otherwise repository operations remain idempotent so retry is safe.
- Synthetic rule persisted state remains only input/date context. Rule provenance continues to resolve at calculation time through `@found-calc/rules`.

## 7. Explicit exclusions

Phase 04 does not include:

- remote D1 creation/migration or Cloudflare deploy/DNS/secrets mutation;
- Xendit, subscriptions, entitlements, invoices, or payment webhooks;
- production tax/legal/marketplace/health/payroll/fiqh rule packs;
- production catalog publishing/SEO administration;
- Admin publishing tools, Goals, Projects, Profiles beyond Better Auth identity, team/collaboration, analytics, or AI explanations;
- calculation history, named saved calculations, sharing, exports, or server-side calculation APIs;
- email verification/reset delivery or OAuth providers.
